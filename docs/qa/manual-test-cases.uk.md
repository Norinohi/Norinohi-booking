# Ручне тестування сайту: план і тест-кейси

Файл для повторного використання, під час прогону не змінюється. Результати всіх прогонів, баги й
те, що лишилось перевірити, ведуться в одному файлі `docs/qa/test-results.uk.md`.

## Правила прогону

- **Оплату не робимо.** Жодних даних картки, жодного натискання «Оплатити» на кроці Payment чи на
  `/bookings/[id]/pay`. Екран оплати можна лише відкрити й перевірити, що він показується.
- **Кожен Confirm (hold) скасовується через адмінку** одразу після перевірки екрана підтвердження:
  `/uk/staff/bookings` -> бронювання -> «Скасувати». У журнал прогону пишемо id бронювання, яхту, дати й
  результат скасування (статус після, чи звільнилась опція в провайдера).
- Hold на локальному сервері створює **реальну опцію в NauSYS / Booking Manager**, тому робимо не більше
  2 hold за прогін (по одному на провайдера) і скасовуємо кожен.
- Hold, заявки й ліди відправляють **листи через Resend** (клієнту й на STAFF_EMAIL). Форми надсилаємо
  лише з акаунта тестувальника, з позначкою `QA TEST` у тексті.
- Зміни в адмінці (FAQ, маршрути, налаштування, популярне) робимо лише так, щоб їх можна було відкотити,
  і відкочуємо в тому ж кейсі. Синхронізацію провайдерів не запускаємо.
- Паролі вводить людина. Агент не вводить облікові дані.
- Кейси гостя (U2, U3, U9) потребують окремої сесії без входу, інакше форми логіну редіректять у профіль.
- Кожен знайдений баг: кейс, URL, кроки, очікування, факт, скріншот або текст консолі.

## Середовище

- web `http://localhost:3001`, server `http://localhost:3000`, Postgres `5434`.
- Мови: `uk` основна; вибірково `en`, `de`, `es`.
- Вʼюпорти: desktop 1280x800 і mobile 375x812.
- Акаунти: адмін (staff/admin), звичайний користувач (якщо є), гість (без входу).

## Розподіл на два потоки

| Потік                          | Що                                                                                                     | Кейси                  |
| ------------------------------ | ------------------------------------------------------------------------------------------------------ | ---------------------- |
| A: публічний сайт і бронювання | головна, пошук, карта, сторінка яхти, бронювання до Confirm, профіль, wishlist, форми, мови, мобільний | P, S, M, D, B, U, F, L |
| B: адмінка                     | усі екрани адмінки, скасування hold, створених потоком A                                               | AD                     |

Потік A після кожного Confirm записує id бронювання в журнал, потік B (або A у своїй вкладці адмінки)
скасовує його й відмічає результат.
